## v31：近期结果缓存与图层续算

v30 的 FragmentCache 实际上主要是复用内存的对象池，瓦片离开图结构后没有按
坐标保留可再次显示的完整结果。v31 在这个池上增加了近期结果缓存，不复制图像
或群系数组；缓存拥有原来的 Fragment，直到它再次进入视口或被淘汰。

- 默认最多保留 256 张已离开图结构的瓦片，不计入仍在画面内和缓冲区内的瓦片。
  命中后取回原对象，再次离开时放到缓存末尾；容量不足时淘汰最早保留的对象。
- 完整瓦片返回时直接显示，群系、图像与结构列表一起复用，不重新发起预测。
- 未完成瓦片按图层保存进度。已发出的有效查询会先返回结果，再在下一图层或
  下一请求前取消。回来后跳过已完成且版本仍有效的图层。仅完成淡入设置的空瓦片
  不占近期缓存。
- 快速移出又移回同一坐标和维度时，还可接回正在运行的原任务。这个过程只改变
  是否需要它的标记；不会让两个线程写同一瓦片，也不会改变运行中任务的坐标。
- 图层有持久的版本号，局部刷新中途停止后，未完成/失效图层仍会重新加载。区块
  状态变化会淘汰对应位置的缓存，同时标记还在退出的旧查询，防止晚返回的旧结果
  重新进入缓存。全量状态刷新、图层/样式刷新及维度切换保守失效近期缓存；关闭
  或切换世界会清空整个缓存，不跨种子共享。

这是进程内缓存，不写入磁盘。群系与两个常规图像缓冲每张约 100 KiB，256 张
约占 25 MiB 的这部分数据，另有结构列表和对象开销。这些缓冲来自既有对象池，
没有因缓存命中而再复制一套；大量可见瓦片与缓存并存时，对象池仍可能扩容。
容量可通过 JVM 参数调整（0–1024，0 关闭近期结果缓存）：

```powershell
java '-Damidst.fragment.retainedTiles=256' '-Damidst.gtnh.profileQueries=true' -jar build/release/amidst-gtnh-biomes-v0-2-v31.jar
```

## v31：沿已生成/未生成的边界传播权重

每次派发任务时，对当前待生成瓦片建立四邻接图，以已经完成的瓦片作为多个起点，
用最短路径传播距离权重。近期缓存里相邻的完整瓦片也可作为起点。下一张瓦片按
以下顺序选择，顺序由高到低：

1. 当前可见区域优先于屏幕外的缓冲区。
2. 距离已生成边界的传播代价越小，越早生成。完成瓦片的起点代价为 0；正在加载
   的瓦片作为较弱的起点，代价为 2；传播到每个四邻接瓦片再加 1。
3. 同一传播距离下，邻接完成区域越多越优先，先补凹处和空洞。每个已完成邻居
   加 4 分，每个正在加载的邻居加 1 分。
4. 仍相同时按行、列稳定选择，从上到下、从左到右，沿边缘补齐。

不再使用到画面中心的距离。当视口与已有结果完全断开时，才从可见区域左上侧
建立新起点；第二个并行任务可以沿第一个进行中的任务继续扩展。拖动、查询完成
或缓存恢复后都会使用当前状态重新计算排序，避免旧优先级留在执行器中。

上述权重影响生成次序，不影响群系、结构算法或采样分辨率。GTNH 仍默认同时
加载 2 张瓦片；已经发送的单次 Worker 查询仍需自然返回，不中断游戏线程。

### v31 调试与维护

双击测试包的 profile-viewer.bat，在 viewer-profile.log 搜索 GTNH scheduling：

- retained：当前保留的离屏瓦片数；cacheHits：取回已保留或正在退出任务的累计次数。
- evicted：容量不足或数据失效导致的累计淘汰数。
- retired：处理完的离屏通知数，包含缓存保留、回收和移回视口后撤销退出的通知。
- active、pending、scheduled、cancelled、failed 沿用调度统计含义。
- order=frontier 表示当前使用边界调度。GTNH performance 仍记录实际发出的请求耗时。

源码入口：

| 文件 | 修改内容 |
| --- | --- |
| FragmentCache.java | 近期缓存容量、淘汰、坐标/维度索引、所有权交接与失效 |
| Fragment.java | 已完成图层位图、各图层版本、数据维度 |
| LayerLoader.java | 图层版本比较、失效依赖与未完成图层续算 |
| FragmentFrontier.java | 起点代价、邻接分数、四方向传播与稳定排序 |
| FragmentQueueProcessor.java | 派发、取消、完成通知和调度日志 |
| GtnhBiomeWorkerClient.java | 保留已发出请求的成功结果，在下一请求前取消 |

回归测试覆盖完整结果复用、部分图层续算、运行中任务移回、缓存容量和淘汰顺序、
局部/全量失效、维度隔离、失败数据处理，以及边界推进、凹处优先、四邻接传播、
弱起点和可见区域优先。另有实际 TCP 测试确认拖动后仍能保存正在返回的查询结果。
尚未测量完整 GTNH 游戏中的实际转向延迟或缓存命中率。

人工对比建议：在相同种子、图层和缩放下，先拖过几屏，再回到刚看过的位置；
应观察到 cacheHits 增长，完整缓存瓦片不再新增 biomes/structures 请求。再在生成
途中反向拖动，确认已完成图层被复用、缺口从现有边界继续补齐。

## v30 历史：生成途中改变拖动方向

旧调度器使用 FIFO，并在整批加载结束后才再次处理回收队列。因此已经移出
画面的任务仍会执行。它还用 `getActiveCount()` 判断能否提交任务，但在执行器
线程真正开始前这个数字不会增加，可能把大量任务提前放入执行器队列。
运行中的瓦片若暂时不能回收，原实现会丢掉回收通知，之后也不会重新尝试。

v30 的处理顺序如下：

1. EDT 在每次更新画面时发布不可变的视口范围。调度线程不遍历可变的地图图结构。
2. 每个调度 tick 先消费完成通知、回收不再需要的瓦片，再按当前视口选择任务。
   可见瓦片优先于屏幕外的缓冲瓦片，同一类中优先选择靠近画面中心的瓦片。
   新旧视口重叠区域的有效任务继续使用；不会因每个像素的拖动而全部重算。
3. 离开图结构的瓦片立即标记回收，未开始的任务从队列剔除。已经开始的任务在
   图层之间、发起下一次 Worker 请求前检查取消，避免继续生成旧位置的结构等图层。
4. 提交到线程池前先占用瓦片和并发名额。GTNH 默认最多同时加载 2 张瓦片，
   与 CPU 核心数解耦；普通模式仍使用原有线程数设置。
5. 运行中的任务实际退出、完成通知被调度器消费后，才能复用其数据缓冲区。
   回收通知会一直保留到可回收为止。切换维度和关闭世界也经过取消与释放流程。
6. `world_state` 改为最多一个后台请求，不再阻塞调度。首次异步结果建立基线时
   会刷新已使用瓦片，避免遗漏等待期间发生的区块变化。

调度 tick 仍由现有的 20 ms 定时器驱动，不等待整批加载完成。**这不代表新瓦片
会在 20 ms 内生成完成**：GTNH 世界访问仍由游戏线程串行执行。已发送的单次查询
会自然返回或超时，之后取消旧任务；没有中断游戏线程，也没有增加 Worker 取消协议。
特别慢的单次 `structures` 请求仍可能影响转向响应。这种情况的下一步应是按区块
拆分 Worker 查询并增加协作取消点，需另外验证预测顺序、缓存与游戏 tick 开销。

这次改动在 Viewer，兼容 v29 的 Worker（协议 18）；测试包也附带同一 Worker。
若仍使用更老的 Worker，请一并更新，以保留 v29 的算法优化和之前的崩溃修复。
没有降低采样分辨率或更改预测算法。

### 调试与调参

测试包的 `profile-viewer.bat` 同时开启请求计时与调度统计。搜索 `GTNH scheduling:`：

- `active=2/2` 表示当前占用和上限，包含已提交但尚未完成处理的任务。
- `pending` 是待调度队列长度；它可能包含等待合并的重复刷新通知。
- `scheduled`、`cancelled`、`recycled`、`failed` 是当前世界生命周期中的累计计数。
  正常拖动会增加取消和回收计数；`failed` 表示未成功且非正常取消的加载任务。

日志有变化时最多每秒记录一次。诊断关闭时不输出调度日志。若需要对比并发量：

```powershell
java '-Damidst.gtnh.profileQueries=true' '-Damidst.gtnh.concurrentFragments=4' -jar build/release/amidst-gtnh-biomes-v0-2-v30.jar
```

`amidst.gtnh.concurrentFragments` 默认 2，限制到 1–4，且不超过 Viewer 的线程池大小。
较高值可能提高持续生成的吞吐量，同时也会让更多旧查询进入 Worker；应结合
同一场景的转向等待与 `queue`、`compute` 耗时来选择。无需重启游戏来调整这个 Viewer 参数。

### 验证方式

`FragmentQueueProcessorTest` 使用可控制的执行器和实际图层加载流程，验证 100 张
待生成瓦片不会突破并发上限、可见区域与中心优先、拖动保留重叠区域、阻塞查询
期间可继续调度、旧写入结束前不复用缓冲、维度切换、加载期间的重复区块刷新和
关闭后的旧任务隔离。`GtnhWorldStatePollerTest` 验证异步单请求、初次刷新和重试。
客户端 TCP 测试覆盖取消等待 Worker 的旧任务后，当前任务仍能正常连接。

这些是调度和连接回归测试，没有测量完整 GTNH 游戏中的实际转向延迟。
人工测试建议：同一种子、缩放与图层，先向未预测区域拖动，在瓦片仍空白时迅速
反向拖动。检查新位置是否优先补齐，回头是否正常加载，并保留 `viewer-profile.log`。

维护入口：`FragmentViewport` 管排序；`FragmentQueueProcessor` 管派发、完成和回收；
`FragmentManager` 管并发默认值与 EDT 入口；`TaskCancellation` 管任务范围内的取消；
`LayerLoader` / `GtnhBiomeWorkerClient` 提供取消检查点；`GtnhWorldStatePoller` 管异步轮询。

## v0.2 相比 v0.1 增加了什么

仓库中 `4ca3fe1c` 的父提交标记为 `v0.1-v13`。当时
`gtnh/worker/mod/SurfaceBiomeSampler.java` 直接调用 RWG 的
`getBiomeDataAt(x,z)`，再判断河流。v0.2 为了还原 RWG 最终的群系边界，
增加了 `ChunkGeneratorRealistic#getNewNoise` 中的群系混合与噪声选择过程。

一张 Viewer 主世界瓦片覆盖 512×512 方块，取 128×128 个显示样本，会涉及
32×32＝1,024 个区块。v0.2 每个新预测区块收集 21×21 个邻域样本，计算
25 个混合点；每个混合点累加 17×17 个权重，随后进行多轮插值。
因此首次拖到未预测区域时，计算量明显大于 v0.1 的直接查询。

此外，旧缓存把坐标直接打包成 `Long`，其 `hashCode` 等价于 `x ^ z`。
RWG 的规则网格上大量不同坐标得到相同哈希值，缓存命中本身也比较昂贵。
单一群系的提前结束判断原本在全部 25 个混合点计算之后；非河流位置也会
因为 Java 的参数求值规则调用河流噪声函数。

## v29 的改动和正确性约束

改动集中在 Worker 的 `SurfaceBiomeSampler.java`，继续使用 v0.2 的规则：

1. 给坐标键增加可逆的 64 位混合，保留唯一性并分散哈希桶。
2. 首先计算中心混合点，若满足 RWG 原有的 `>0.95F` 条件即返回。
3. 每个采样器缓存最多 16,384 个八方块网格混合点；相邻区块可以直接复用。
   缓存存储原始浮点权重和对应 ID，每次映射到当前区块的紧凑 ID 表。
4. 河流强度不足时跳过河流噪声计算。

浮点累加仍按原来的 X/Z 循环顺序执行，插值、候选 ID 顺序、选择噪声、
河流阈值以及 4×4 显示单元的中心坐标均保留。已加载区块仍优先使用实际群系。
所有缓存都属于各自的种子/世界采样器，并设置容量上限；没有将游戏世界访问
移到网络线程。

`ReferenceRwgSurfaceBiomeSampler.java` 冻结了修改前的 v0.2/v28 算法，
只存在于测试源码。对照测试覆盖 58,806 个采样坐标、负坐标、大坐标、完整及
四分之一分辨率、重复查询、缓存淘汰，并逐项核对 121 个区块的全部插值权重。

## 可复现基准

在仓库根目录，使用 Worker 构建所需的 JDK 25：

```powershell
.\gtnh-worker\gradlew.bat -p gtnh-worker benchmarkSurface '-Pgtnh.modules.codeStyle=false' --offline
```

结果保存到 `gtnh-worker/build/reports/performance/surface-biomes.json`。
基准对新旧实现交替测量，分别预热 3 次、采集 7 次并取中位数；堆上限 512 MiB。
固定种子 123456789，连续预测 4 张此前未缓存的 512×512 方块瓦片，步长 4。

2026-09-08，本机 Azul JDK 25 的结果：

| 固定输入场景 | 修改前 v0.2 | v29 | 算法基准提速 |
| --- | ---: | ---: | ---: |
| 单一群系 | 209.381 ms | 59.215 ms | 3.54 倍 |
| 多群系边界 | 213.679 ms | 96.711 ms | 2.21 倍 |

两组结果校验值一致。两种实现调用原始群系查询的次数也一致，均为 22,825。
噪声调用分别从 65,536 降至 8,400、从 130,128 降至 72,992。

基准使用固定、种子驱动的群系/噪声输入，只衡量混合、缓存和反射路径的成本。
它不包含实际 RWG 原始查询的成本、游戏线程排队、TCP 和结构图层，因此不能
把这里的倍数直接当作完整游戏中的地图加载倍数。v0.1 与 v0.2 的预测规则有
区别，本表比较的是修改前后的 v0.2。

## 在实际游戏中定位剩余耗时

配套使用 v29 Viewer 和 Worker，保持游戏运行，用下列方式启动 Viewer：

```powershell
java '-Damidst.gtnh.profileQueries=true' -jar build/release/amidst-gtnh-biomes-v0-2-v30.jar
```

测试包也提供可双击的 `profile-viewer.bat`，日志写入 `viewer-profile.log`。
诊断按请求开启，无需为开关性能日志重启游戏或编辑 Worker 配置。
正常启动时诊断关闭，Worker 不读取计时器或增加计时字段。

在原生控制台/日志中搜索 `GTNH performance:`：

- `biomes`：群系瓦片；`structures`：结构预测；`world_state`：已加载区块状态。
- `total`：Viewer 观察到的请求耗时，包括连接、等待、解析等。
- `queue`：请求进入游戏线程队列后，到开始执行之间的等待时间。
- `compute`：Worker 在游戏线程执行该请求的时间。

如果 `compute` 高，检查对应的预测算法和缓存；如果 `queue` 高，检查游戏
tick、其他预测请求、是否暂停或正在加载。`total` 还包括网络执行器排队和 JSON
处理等成本，不能把 `total - queue - compute` 全部归为网络传输。
较旧的 Worker 会忽略可选诊断字段，Viewer 显示 `unavailable`；协议号仍为 18。

比较不同版本时使用相同种子、维度、缩放和图层，分别重新启动 Viewer/GTNH
清空缓存，再沿相同方向拖动相同距离。分别记录主菜单和已进入存档两种状态。
避免用一个版本的首次冷查询去对比另一个版本已缓存的区域。
